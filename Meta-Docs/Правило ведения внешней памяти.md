# Регламент ведения внешней памяти (Git State Management)

Этот документ определяет правила поддержания актуального состояния проекта в Git-репозитории. Цель — обеспечить бесшовную передачу контекста другим чатам при исчерпании лимитов окна, а также быстрое выделение и делегирование отдельных задач в середине работы без потери логики и лишнего расхода токенов.

## 1. Триггеры записи в Git (Когда обновлять данные)
Не делай коммиты на пустые реплики, уточняющие вопросы или промежуточные рассуждения. Синхронизируй состояние с репозиторием строго в момент фиксации значимого результата:
- Утверждены или скорректированы критерии, требования или бизнес-логика.
- Получен валидированный, рабочий инструмент (чистый код, формула, промпт-шаблон, алгоритм).
- Поставлена, декомпозирована, изменена или закрыта отдельная задача/подзадача.
- Принято ключевое архитектурное решение.

## 2. Адаптивная структура хранения (Принцип разделения)
При записи данных в Git ориентируйся на существующую архитектуру папок и файлов репозитория. Не создавай жестких, несовместимых структур. Если выделенной директории под память проекта еще нет, организуй хранение по трем независимым логическим слоям:

1. **Мета-уровень (Состояние и навигация):**
   - *Что хранить:* Глобальная цель, общие ограничения среды/стека, текущий статус проекта, список активных модулей и актуальная «Точка старта» (на чем остановились и какой следующий шаг).
   - *Назначение:* Позволяет новому чату за одно чтение понять общую картину.
2. **Уровень проекта (Ядро и инструментарий):**
   - *Что хранить:* Утвержденные спецификации, общие правила, архитектура и валидированный инструментарий (код, алгоритмы, базовые шаблоны).
   - *Назначение:* Единый источник истины для всех участников и чатов.
3. **Уровень задач (Модульная декомпозиция):**
   - *Что хранить:* Локальные критерии, входные/выходные параметры и статус конкретных задач или подзадач. Выноси крупные подзадачи в отдельные, изолированные файлы с самоговорящими названиями.
   - *Назначение:* Позволяет делегировать отдельную подзадачу другому чату, передав ему ссылку только на этот локальный файл и мета-уровень.

*Правило масштабирования:* Разбивай крупные файлы на более мелкие модули по мере роста проекта, чтобы при чтении не перегружать контекстное окно узких чатов.

## 3. Правила чистоты и экономии токенов (Жесткий фильтр)
- **Актуализация вместо истории:** Не дописывай новые выводы поверх старых, если старые устарели. Перезаписывай блоки так, чтобы файлы всегда отражали только последнее **одобренное** состояние.
- **Проверка связей при перезаписи:** Если новое решение меняет логику ранее сохраненных блоков, скорректируй их так, чтобы в репозитории не оставалось внутренних противоречий.
- **Запрет на информационный шум:** Никогда не сохраняй тупиковые ветки рассуждений, исправленные ошибки, черновики и сгенерированный конечный продукт (большие массивы данных, списки результатов, сырые логи). Фиксируй только логику, правила и инструменты.
- **Максимальная плотность:** Пиши телеграфным стилем, без воды и вежливых оборотов. Экономь каждый токен при записи и последующем чтении.

## 4. Маркер синхронизации в чате
После каждого успешного обновления файлов в репозитории добавляй в самый конец своего ответа в чате короткую техническую строку:
`[GIT SYNC: обновлены <путь/к/файлам> | суть изменения в 3-5 словах]`
