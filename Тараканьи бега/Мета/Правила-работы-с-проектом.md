# Мета-правила проекта «Тараканьи бега» / Roach Rush

Версия: 1.0  
Назначение: единые правила работы ChatGPT, других ИИ-чатов и исполнителей с проектом.

## 1. Роли и ответственность

**ChatGPT в основном оркестраторском чате**
- Владелец продуктового контекста: продакт-менеджмент, геймдизайн, приоритизация, архитектурные решения на уровне продукта.
- Ведёт единую Матрицу разработки: этапы, фичи, текущие статусы, исполнители и критерии готовности.
- Анализирует текущую игру, формулирует решения и готовые задания исполнителям.
- Проверяет результаты делегированной работы и организует переход между крупными этапами.
- Сам выполняет работу, которая не требует отдельного большого кодового контекста: анализ, проектную организацию, документацию, постановку задач, небольшие согласованные исправления.

**Кодовый агент / отдельный чат**
- Подключается для крупной, изолируемой задачи: значительная игровая функция, переработка подсистемы или объёмная техническая работа, которая существенно расходует контекст основного чата.
- Получает минимально достаточный комплект: актуальный HTML или необходимые файлы, конкретное ТЗ, нужные выдержки из GDD, критерии результата и требования к фиксации результата в GitHub.
- Возвращает законченный результат, а не набор несвязанных фрагментов. Ключевые решения и ограничения записывает в проектную документацию.
- Не должен заново исследовать весь проект, если для задачи достаточно переданного файла и спецификации.

**QA-агент**
- Основная проверка прототипа уже выполнена Agent-Qwen в десктоп-чате. Считать её пройденной по подтверждению владельца проекта.
- Повторный полный QA не является ближайшей самостоятельной задачей. После существенных изменений проводить целевую регрессионную проверку затронутых систем.

**Пользователь / владелец продукта**
- Принимает решения и проверяет результат на крупных контрольных точках: готовый прототип, Web MVP, софт-лонч, инвест-готовность и другие большие вехи.
- Не вовлекается в согласование каждого изменения, промежуточного файла или микрозадачи.
- Даёт доступы или подтверждает решения только там, где это действительно невозможно выполнить без владельца (например, первоначальный доступ к игровому хостингу или секреты автоматического деплоя).

## 2. Когда делегировать

Делегирование нужно для сокращения срока разработки, параллельной работы и сохранения контекста основного чата. Само по себе наличие задачи не является поводом создавать новый чат.

**Делегировать стоит, когда одновременно выполняются условия:**
- задача крупная или потребляет существенную часть контекста;
- её можно изолировать от остальной разработки;
- исполнителю достаточно конкретных файлов и самостоятельного ТЗ;
- результат можно принять как законченный блок;
- ход работы не требует постоянных решений основного продакт-чата, а ключевые результаты можно отразить в документации.

**Оставлять в основном чате:**
- продуктовые и геймдизайнерские решения;
- анализ игры и приоритизацию;
- организацию GitHub и документации;
- небольшие исправления и точечную доработку;
- проверку, интеграцию и приёмку результатов.

Не делегировать мелкие правки только ради формального распараллеливания. Не просить пользователя вручную переносить промежуточные сведения между чатами, если это можно зафиксировать в репозитории.

## 3. Единый источник плана и статусов

Единственный актуальный сводный документ планирования — **Матрица разработки**:

`roach-arcade/docs/Матрица-разработки.md`

Она одновременно содержит:
- перечень функций и результатов;
- распределение по этапам;
- текущий статус;
- ответственного исполнителя;
- комментарии, ограничения и критерии готовности.

Не создавать отдельные документы roadmap, feature-list, статусную таблицу или список исполнителей, дублирующие Матрицу разработки. GDD, продюсерский питч и арт-дирекшен остаются тематическими документами и не заменяют матрицу.

## 4. Фиксация результатов в GitHub

Ключевые результаты общения в основном чате и делегированных чатах должны отражаться в проекте GitHub сразу после получения законченного результата.

- Продуктовые решения, этапы, фичи, статусы и исполнители — в Матрице разработки.
- Правила взаимодействия, делегирования, идентификации сообщений и приёмки — в этом документе.
- Состояние и назначение папок/файлов — в Реестре проекта.
- Подробности игровых систем — в GDD.
- Изменение продуктовой концепции или инвест-направления — в продюсерском питче.

Не вести параллельные журналы, если та же информация уже зафиксирована в одном из этих документов. Обновлять существующий источник истины, а не создавать его копию.

## 5. Приёмка без бюрократии

- Пользователь проверяет только крупные контрольные точки.
- Между ними исполнители самостоятельно выполняют необходимые проверки.
- Отдельно докладывать нужно о завершении крупной задачи, существенном риске, конфликте требований или решении, которое невозможно принять без владельца.
- Не создавать отдельный отчёт на каждый коммит.
- Не заводить GitHub Issue на каждое мелкое исправление.
- Результат делегированной работы должен содержать краткое описание сделанного, затронутые файлы, проверки и оставшиеся ограничения.

## 6. Правило идентификации сообщений (ID)

Каждому сообщению основного чата, которое содержит законченный результат — ответ, анализ, разбор, решение или завершённый пакет работы, — присваивается краткий самоговорящий ID.

Формат — отдельной строкой в самом начале сообщения:

`**ID:** [№_Сообщения]_[Краткое_Название]_v[Версия]`

Правила:
- счётчик сообщений начинается с 1-го и увеличивается для каждого законченного фрагмента работы в рамках текущего чата;
- при доработке того же результата увеличивается версия: v1, v2, v3 и далее;
- при существенном ответвлении или новом ракурсе создаётся новое смысловое название;
- ID должен позволять однозначно сослаться на конкретное сообщение и конкретную версию;
- ID не заменяет запись результата в GitHub: важное решение всё равно фиксируется в соответствующем документе.

## 7. Работа с версиями и файлами

- Перед правкой проверять, какой файл является каноническим.
- Текущая игровая версия — `roach-rush.html` в корне папки проекта.
- Не использовать ранний `roach-arcade/index.html` как источник разработки.
- Не удалять и не перезаписывать резервные материалы без проверки назначения и явного решения владельца.
- Сначала фиксировать новое состояние и реестр, затем предлагать очистку устаревших копий отдельным решением.
- Не восстанавливать несуществующие `parts/`, `build.sh` или тесты из устаревшего README без технической необходимости.

## 8. Разделение этапов

- **Прототип:** проверка базовой игровой гипотезы и работающего игрового цикла.
- **Web MVP:** стабильная и законченная веб-версия, пригодная для публичной демонстрации. Без рекламы.
- **Софт-лонч:** ограниченный запуск, аналитика, измерение поведения и тестирование рекламной монетизации.
- **Инвест-пакет:** доказательства продукта, презентация, план финансирования и понятная программа развития.
- **Итерации 2–3:** развитие и масштабирование на основании данных, финансирования и продуктовых решений.

Реклама и SDK рекламных сетей не входят в прототип и Web MVP. Полноценный QA прототипа уже пройден и не должен повторно планироваться как отдельная ближайшая веха.

## 9. Правило минимизации действий пользователя

Приоритет — самостоятельная работа ИИ и автоматизация:
- не просить пользователя вручную собирать статусы и переносить документы;
- не задавать повторно вопросы, на которые уже есть ответ в проекте;
- не разбивать крупный результат на множество мелких согласований;
- запрашивать участие пользователя только для продуктового выбора, доступа или приёмки контрольной точки.
