# Регламент ведения проекта HDMS и непрерывности работы между чатами/агентами

**Статус:** обязательный регламент проекта.  
**Дата:** 17 ноября 2026.  
**Назначение:** обеспечить непрерывную работу над HDMS несколькими чатами и агентами без зависимости от памяти отдельного диалога.

## 1. Базовый принцип

GitHub — единый долговременный источник актуального контекста проекта. Чат, агент или исполнитель не считается носителем единственной важной информации. Любое принятое продуктовое решение, подтверждённый технический факт, изменение статуса, ограничение, результат исследования и следующий шаг, которые могут понадобиться другой сессии, должны быть зафиксированы в соответствующем документе репозитория.

Документы описывают состояние самого проекта. В них не ведётся повествование о том, «в каком чате это обсуждалось», кто из ИИ что вспомнил или откуда перенесли заметку. История изменений фиксирует изменение проекта, а не историю переписки.

## 2. Иерархия источников истины

При противоречиях использовать следующий порядок:

1. **Текущий код и воспроизводимые проверки** — истина о том, что реально реализовано и работает.
2. **PROJECT_GOVERNANCE.md** — правила ведения проекта, фиксации контекста, ролей и передачи работы.
3. **09_roadmap.md** — актуальные приоритеты, статусы, блокеры и следующие задачи.
4. **Профильные документы** — истина в своей области: vision, tech spec, rules, feature list, competitor analysis, user guide, reverse-engineering package.
5. **CHANGELOG.md** — журнал изменений документации и значимых проектных изменений; не замена профильным документам.
6. **Архивы, ZIP, старые снимки и исторические композиты** — только исходные материалы для извлечения фактов. Они не являются актуальным источником после переноса и проверки сведений.

Если источники расходятся, не выбирать удобную версию молча: зафиксировать конфликт, проверить код/первичный материал и обновить канонический документ.

## 3. Обязательный цикл каждой рабочей сессии

### Перед началом

1. Открыть актуальный `main` и проверить последние изменения.
2. Прочитать `HDMS/docs/START_HERE.md`, `09_roadmap.md` и профильные документы своей задачи.
3. Проверить текущие статусы, открытые вопросы, незавершённые изменения и ограничения.
4. Не повторять уже закрытые исследования и не восстанавливать факты по памяти, если они есть в GitHub.
5. Если задача затрагивает код, изучить актуальную реализацию и тесты; если документацию — проверить связанные документы и ссылки.

### Во время работы

1. Разделять подтверждённые факты, выводы, гипотезы и неизвестное.
2. Не повышать статус функции до Implemented/Verified/Done без соответствующего основания.
3. Не менять несвязанные документы и код «заодно».
4. При обнаружении нового устойчивого факта сразу определить, какой профильный документ является его домом.
5. Если решение требует владельца, записать вопрос и варианты, но не выдавать предположение за принятое решение.

### Перед завершением

1. Обновить профильные документы, которых касаются результаты.
2. Обновить Roadmap, если изменились статус, приоритет, блокер или следующий шаг.
3. Обновить CHANGELOG для значимых изменений.
4. Проверить ссылки, названия файлов, даты, согласованность терминов и отсутствие противоречий.
5. Зафиксировать изменения в GitHub отдельным понятным commit.
6. Сообщить краткий реестр: какие файлы созданы/обновлены, что именно изменилось, commit, что осталось незавершённым и что требуется от владельца.
7. Не заявлять об изменении, если оно не записано и не проверено в GitHub.

## 4. Как распределять контекст по документам

Не складывать весь проект в один гигантский handoff. Каждый факт записывать в один профильный источник, а в остальных местах оставлять короткую ссылку.

| Тип информации | Канонический документ |
|---|---|
| Продуктовая цель, позиционирование и границы | `01_vision.md` |
| Состав функций и статус продуктовых возможностей | `02_feature_list.md` |
| Доноры, конкуренты, сравнительные основания | `03_competitor_analysis.md` |
| Фактическая архитектура и технические контракты | `04_tech_spec.md` |
| Исходные требования и исторический task pack | `05_task_pack.md` |
| Монетизация и коммерческие гипотезы | `06_monetization.md` |
| Реальные правила, покрытие и приближения движка | `07_rules_and_approximations.md` |
| Текущий приоритет, статус, блокеры, следующий шаг | `09_roadmap.md` |
| Запуск и использование приложения | `USER_GUIDE.md` |
| Периметр, роли, спецификации и evidence для деконструкции | `HDMS/reverse-engineering/` |
| Регламент нескольких чатов/агентов и непрерывности контекста | `PROJECT_GOVERNANCE.md` |
| Краткая хронология значимых изменений | `CHANGELOG.md` |

Контекстный handoff — это компактная карта текущего состояния и ссылок на профильные документы. Он не должен дублировать всю документацию или хранить сведения только потому, что они пришли из отдельной переписки.

## 5. Правило многосессионной работы

- Все чаты и агенты работают с одним репозиторием и одной актуальной веткой, если для отдельной задачи не создана изолированная ветка.
- Перед редактированием проверять свежий HEAD; не перезаписывать чужие коммиты устаревшим деревом.
- Параллельные исполнители получают непересекающиеся файлы/задачи либо работают в отдельных ветках.
- При конфликте изменений — остановить запись, получить свежий HEAD и согласовать объединение.
- Каждый исполнитель оставляет репозиторий в понятном состоянии: изменения закоммичены либо явно перечислены как незавершённые.
- Не хранить единственную копию важного решения в сообщении чата, локальной заметке агента или его внутренней памяти.

## 6. Стандарт handoff для нового чата/агента

Новый исполнитель должен иметь возможность начать работу, прочитав только:
1. `START_HERE.md`;
2. `PROJECT_GOVERNANCE.md`;
3. `09_roadmap.md`;
4. профильные документы своей задачи;
5. актуальный код и тесты, если задача техническая.

В handoff указывать только:
- цель текущей задачи;
- конкретный объём работы;
- ссылки на канонические документы и файлы;
- уже принятые решения и ограничения, если они ещё не отражены в профильных документах;
- текущий статус и критерий завершения;
- открытые вопросы и требуемые действия владельца.

Не пересказывать всю историю диалога, не перечислять происхождение сведений по чатам и не просить пользователя повторять то, что уже записано в GitHub.

## 7. Запрет на потерю контекста

Задача не считается завершённой, если важные результаты остались только в переписке. Если сессия заканчивается из-за лимита контекста, передачи другому агенту или смены исполнителя, сначала обновить документы и Roadmap, затем передать ссылку на commit и краткий handoff.

## 8. Выбор ИИ-агентов и инструментов

Роль определяется не названием модели, а фактическими инструментами и правами.

Для первичной деконструкции предпочтителен агент, который умеет работать с репозиторием: читать дерево и файлы, искать символы, переходить по зависимостям, запускать разрешённые тесты, фиксировать commit SHA и сохранять результаты в документы.

**Qwen Code и Qwen-Agent — разные продукты:**
- Qwen Code — CLI coding-agent с файловыми/терминальными инструментами, MCP, режимом планирования и специализированными subagents. Это более подходящий кандидат для автономного исследования клона репозитория, если подключены нужные MCP и права.
- Qwen-Agent — Python-фреймворк для создания собственных агентов. Сам по себе это не готовый агент, подключённый к GitHub пользователя; потребуется собрать приложение, настроить модель, MCP/tools и разрешения.
- Наличие MCP не означает, что GitHub MCP уже подключён. Перед стартом проверить список инструментов и выполнить read-only тест чтения назначенного репозитория.

**Рекомендация HDMS:** испытать Qwen Code с выбранной Qwen-моделью на одной функции и одном назначенном доноре. Дать read-only доступ к репозиторию донора и право записи только в отдельную ветку/папку исследовательских результатов HDMS. Не выдавать права записи в основной код HDMS. Оценить полноту, точность ссылок на файлы/строки, evidence register, пропуски сценариев и стоимость. После пилота решить, масштабировать ли его.

ChatGPT рационально использовать для продуктовых решений, архитектурной оценки, проверки спецификаций, устранения противоречий и clean-room handoff. Не обязательно тратить дорогой контекст основного чата на массовое чтение каждого файла донора, если другой агент справляется надёжно.

Выбор Qwen не считается заранее доказанным преимуществом. Сравнивать агентов на одинаковом небольшом задании по полноте, точности ссылок, неподтверждённым выводам, затратам и безопасной работе с Git.

## 9. Применение к clean-room

Этот регламент не отменяет и не ослабляет clean-room. Исследовательские документы, исходники и evidence остаются в исследовательском контуре. Для разработчика формируется отдельный очищенный пакет. Сам факт хранения всех проектных документов в одном репозитории не означает, что каждому агенту предоставляется доступ ко всем каталогам: доступ ограничивается ролью и назначением.
