## Итоговый вывод

1. По базовым функциям HDMS не уступает конкурентам.
2. По визуальному конструктору — конкурирует с FindStone и Firestone.
3. **По симуляции matchup (winrate, ход, HP) — единственный.** Это уникальное торговое предложение.
4. По winlines — единственный, кто генерирует их из симуляции, а не из реальных игр.
5. **По быстрому циклу «правка → тест → дельта winrate» — единственный.** Killer-фича.
6. По overlay и реальной статистике — проигрывает, но это не конкуренция, а дополнение.
7. По мобильности (PWA) — выигрывает у HDT/Firestone (десктоп), проигрывает FindStone (нативный iOS).
8. По цене — может конкурировать с бесплатными через Free+Premium ($3–5/мес).

## Что копировать у самой Hearthstone

**Не нужно.** Другие сервисы (HSReplay, Firestone, FindStone) уже скопировали UI-паттерны Hearthstone. Достаточно взять их интерфейсы — это быстрее и юридически безопаснее.

**Изображения карт** — легально через HearthstoneJSON (URL картинок в объекте карты). Звуки и анимации не копировать (юридический риск, для калькулятора не нужны).

## Reverse engineering: инструменты и метод

Screenshot-to-code и Anima полезны только как вспомогательный способ получить черновую вёрстку из изображения. Они не раскрывают поведение, DOM, сетевые запросы, состояние интерфейса и правила игры. Не использовать сгенерированную по скриншоту разметку как готовую спецификацию.

Основной порядок исследования:
1. Browser DevTools — DOM, computed styles, accessibility, responsive viewports, события и Network.
2. Playwright + Trace Viewer — повторяемые пользовательские сценарии, screenshots, DOM snapshots, console и network traces.
3. Chrome DevTools Recorder — быстрая запись и повторение действий для последующей автоматизации.
4. OBS Studio — ручная видеозапись динамических состояний и взаимодействий, которые не передать одним скриншотом.
5. mitmproxy / mitmweb — только дополнительный инструмент, когда DevTools недостаточно для разрешённого анализа сетевого обмена.
6. Fireplace / Metastone и другие open-source реализации — технические reference по структуре игровых эффектов; проверять лицензии перед повторным использованием кода.

Подробный протокол, чек-лист скриншотов/видео, роли ChatGPT и владельца, методика анализа карточных механик и нескольких winlines описаны в [REVERSE_ENGINEERING_PLAN.md](./REVERSE_ENGINEERING_PLAN.md).

**Важно:** сравниваем доступное поведение и пользовательские сценарии. Не обходим логины, платный доступ, DRM, античит и технические ограничения; не копируем чужой закрытый код, графику и тексты.

## Актуализация анализа на 16 ноября 2026

### Как читать колонку HDMS

Таблица выше сформирована как продуктовый сравнительный анализ и включает целевые возможности HDMS. Зелёная отметка не означает, что функция полностью готова, прошла acceptance и подтверждена в пользовательском сценарии. Текущий статус кода описан отдельно в [02_feature_list.md](./02_feature_list.md), фактическая архитектура — в [04_tech_spec.md](./04_tech_spec.md).

В текущем MVP:
- A vs B симуляция работает в локальном запуске владельца, но модель предварительная;
- Matrix API и вычислительная функция существуют, но пользовательский ввод Matrix требовал исправления и должен проверяться в браузере;
- Winlines представлены тремя отобранными примерами, а не библиотекой всех партий;
- журналы игр урезаны и не позволяют восстановить полный матч;
- текущий WinPath — пять эвристических групп, а не распознавание самостоятельных линий;
- реальная статистика миллионов матчей не собирается.

### Evidence-first reverse engineering

Для каждого изучаемого сценария нужно фиксировать цель пользователя, начальное состояние, шаги, ответ интерфейса, network request/response (без секретов), ошибки, время ожидания и вывод для HDMS. Одного главного скриншота мало для понимания интерактивного поведения.

Обязательные потоки для первичного сравнения:
1. Импорт deck-кода и открытие состава колоды.
2. Поиск/фильтры и добавление/удаление карт.
3. Просмотр matchup-результата и раскрытие подробностей.
4. Матрица: добавление колод, изменение порядка, запуск и открытие ячейки.
5. История и просмотр отдельного матча.
6. Мобильная версия ключевых сценариев.

Для механик карточной игры нужен отдельный evidence log и воспроизводимый тест. Скриншот интерфейса конкурента не является доказательством корректности конкретного игрового правила.
