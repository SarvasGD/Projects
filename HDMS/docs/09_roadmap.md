# 09 — Дорожная карта HDMS

**Актуальность:** 17 ноября 2026.  
**Принцип:** приоритет у достоверности результата, диагностируемости и основного пользовательского сценария. Старые сроки M1–M6 из исходной концепции больше не являются прогнозом сроков.

## 1. Текущее состояние

### Уже реализовано в коде

- Next.js веб-приложение с разделами A vs B, Matrix, Builder и History.
- Импорт/экспорт deck-кодов.
- Сравнение двух колод через Monte Carlo.
- Варианты запуска A vs B: сервер, Web Worker, параллельные серверные запросы.
- Расчёт матрицы NxN на 2–8 колод на уровне API и симуляционного модуля.
- Конструктор колод и простые карточные фильтры.
- Сохранение A vs B результатов в IndexedDB, экспорт JSON/PNG.
- Dockerfile, Compose, BAT-файлы.
- CI с TypeScript, Vitest, production build, Docker build и Compose validation.

### Проверено автоматическими тестами / CI

Последний подтверждённый кодовый CI до исправления матричного UI:
- TypeScript check пройден;
- 70/70 Vitest tests пройдены;
- Next production build пройден;
- Docker build пройден;
- Docker Compose config пройден.

Unit-тесты матрицы проверяют расчёт NxN с тестовыми fixtures. Они не проверяют ввод deck-кода через UI. Полных browser E2E тестов на момент аудита нет.

### Проверено владельцем локально

Владелец проекта сообщил, что локальный запуск из терминала состоялся и симуляция считает:
- одинаковые колоды на серии около 1000 партий дают примерно 50/50;
- несколько разных пар колод дали на первый взгляд логичные, неслучайные результаты.

Это предварительная ручная проверка, а не независимая валидация игровых правил или точности winrate.

### Найденные и текущие ограничения

- В матричном слоте поле ввода исчезало после первого символа; кнопки подтверждения не было. Добавлен фикс: поле остаётся доступным, есть кнопка «Проверить», декодирование работает с явным кодом и идентификатором слота. Также сбрасываются ранее полученные метаданные после редактирования deck-кода. После CI требуется локальная проверка пользователем.
- Матрица пока выполняется только на сервере; нет Web Worker пути.
- MatrixRecord / IndexedDB store существуют, но история матриц не подключена к интерфейсу.
- A vs B история хранит сводку с тремя выбранными партиями, а не все результаты.
- Каждая партия возвращает только последние 15 записей журнала.
- WinPath — пять эвристических категорий, а не анализ конкретных win conditions.
- Нет распознавания нескольких независимых линий победы.
- Нет отдельного Goldfish mode.
- Нет полноценного реестра покрытия эффектов, версионирования базы карт и предупреждений о неподдерживаемых эффектах.
- Полная модель правил и взаимодействий всех карт в поддерживаемых Constructed-форматах не реализована; существующие обработчики покрывают только часть механик.
- Web Worker не имеет гарантированного офлайн-кэша базы карт: он загружает HearthstoneJSON по сети в свой контекст.
- Нет Playwright E2E и воспроизводимых UI smoke tests.

## 2. P0 — Сделать текущий MVP проверяемым и пригодным для анализа

Это ближайший этап. Не переходить к аккаунтам, монетизации или мобильной упаковке, пока не исправлены базовые проблемы доверия к результатам.

### P0.1 — Основной браузерный сценарий
1. Добавить Playwright smoke tests для A vs B, Matrix, Builder, History.
2. Проверить реальные API-пути: decode, encode, card search/batch, simulate, simulate-matrix.
3. Проверить матрицу после фикса: ввод двух deck-кодов, успешное декодирование, запуск, получение таблицы, обработка неправильного кода и удаления слота.
4. Проверить, что редактирование уже декодированного кода сбрасывает предыдущие метаданные.
5. Добавить логику/сообщения об ошибках, если слот не декодирован.

### P0.2 — Полная история партии
1. Убрать обрезку журнала до последних 15 записей.
2. Логировать каждый значимый шаг: добор, розыгрыш карты, срабатывание эффекта, атаку, размен, потерю существ, изменение HP/брони/маны, усталость, смерть и конец хода.
3. Ввести структуру событий с устойчивым типом, а не только текстом detail.
4. Логировать необходимые снимки состояния или изменения состояния, чтобы можно было воспроизвести партию.
5. Вынести лимит истории в отдельную настройку хранения/экспорта, чтобы полный лог не раздувал обычный ответ без необходимости.
6. Добавить просмотр боя с навигацией по ходам и экспорт полной записи.

### P0.3 — Несколько Winlines и Goldfish — разные задачи

**Winlines matchup:** успешные партии против конкретного оппонента. Нужно сохранять и сравнивать фактические последовательности событий.  
**Goldfish:** самостоятельный тест плана колоды без полноценного взаимодействия противника: насколько часто собирается конкретная комбинация, к какому ходу, с каким темпом/уроном. Goldfish-модуль в текущем коде не найден и не считается реализованным.

Сначала построить событийную телеметрию и базовые метки карт/механик, затем:
1. Развести стратегическую семью (общая идея колоды) и отдельную win line (самостоятельный способ выиграть).
2. Разрешить нескольким линиям существовать в одной колоде, в том числе больше двух.
3. Различать самостоятельные линии, варианты одной линии и смешанные/комбинированные реализации.
4. Определять линию по реально сыгранным и сработавшим событиям, а не только по последнему источнику урона или манакривой.
5. Для каждой линии показывать число партий, долю побед, долю от всех побед, медиану хода победы, распределение и неопределённость.
6. Проверять независимость линии: возможны ли победы, когда ключевые события альтернативной линии не происходят; что происходит в ablation-тесте при удалении соответствующего пакета карт.
7. Не делать «число winlines» самостоятельной оценкой силы колоды. Сила и устойчивость проверяются на нескольких матчапах, с разными seed и вариантами карт.

Первый benchmark: Rogue Dragon-Charge. Отдельно пометить карты/события пакета Imbue, драконов, зарядки/charge и общие карты. Сравнить полную деку, сценарии без ключевого Dragon package, без Imbue package и смешанные победы. Конкретные критерии и правила разметки — REVERSE_ENGINEERING_PLAN.md.

### P0.4 — Полнота моделирования игровых правил и карточных взаимодействий

**Цель — довести симуляционное ядро до полной поддержки механик всех карт в пределах поддерживаемых Constructed-форматов HDMS.** Это самостоятельная центральная цель проекта. Реестр покрытия — инструмент контроля прогресса, а не конечный результат и не замена реализации эффектов.

Объём включает:
1. Полный жизненный цикл матча: старт, mulligan, ходы, мана, добор, усталость, завершение партии.
2. Модель игровых зон и объектов: герой, сила героя, существа, оружие, рука, колода, сброс, создание и перемещение объектов.
3. Все эффекты карт в поддерживаемом scope: боевые ключевые слова, Battlecry, Deathrattle, триггеры, ауры, постоянные эффекты, усиления/ослабления, трансформации, копирование, возврат, секреты, задания, локации и другие применимые механики.
4. Корректный порядок событий и разрешения вложенных/повторных эффектов, выбор и проверку целей, обработку смерти и повторную проверку состояния.
5. Боевые взаимодействия, случайные эффекты, генерацию карт и воспроизводимость через seed.
6. Покрытие всех коллекционных карт, допустимых в поддерживаемых форматах, а также создаваемых токенов и вариантов, которые могут участвовать в матче.
7. Версионированный набор карточных данных, механик, тестов и результатов проверки.

**Исследовательский пакет:** [ТЗ реверс-агенту](../реверс/01_QWEN_REVERSE_TZ.md) и [ТЗ контролёру](../контроль/01_CHATGPT_REVIEW_TZ.md). Для полной модели игровых правил назначенный основной донор — MetaStone. Реверс-инженер не сопоставляет его с другими донорами; независимый проверяющий имеет read-only доступ ко всем пяти донорам и выполняет независимую проверку и точечную перекрёстную сверку.

Порядок внедрения:
1. Создать registry по механике и/или dbfId со статусом: подтверждено тестом / частично / не поддерживается / не проверено.
2. Для каждой карты/механики определить фактический эффект, триггер, цель, область действия и порядок разрешения.
3. Добавить unit-тесты для отдельных механик, затем integration-тесты цепочек и конфликтующих эффектов.
4. Проверить все ручные обработчики по реальному dbfId и актуальному тексту карты. Первоочередная известная проблема: МАТРИАРХ в коде делает добор 2, тогда как в исходном описании проекта указано удешевление соседних карт. До проверки не использовать результаты Dragon-Charge как достоверный анализ этой механики.
5. Выявлять неизвестные и неподдерживаемые эффекты в загруженных колодах; не запускать симуляцию молча как будто все карты поддерживаются.
6. Показывать предупреждения до запуска и включать покрытие/ограничения в отчёт результата.
7. Фиксировать версию и дату карточной базы, а также версию правил симуляции.
8. Проверять игровые инварианты, порядок событий, корректность целей, смерти и взаимодействия эффектов на воспроизводимых сценариях.

**Критерий завершения:** каждая карта и механика в поддерживаемом scope имеет явный статус; статус полной поддержки присваивается только после тестов самой карты/эффекта и существенных взаимодействий с другими механиками. Неизвестные случаи не маскируются generic-обработчиком. Цель — полная карточная физика, а не заранее установленный ограниченный процент покрытия.

### P0.5 — Server / Worker parity
1. Запустить одинаковые коды, games, seed и options на сервере и Web Worker.
2. Сравнивать итоговые счётчики и выбранные партии.
3. Зафиксировать поведение при ошибке Worker и fallback.
4. Убедиться, что Worker не маскирует сетевые ошибки загрузки карты.

### P0.6 — История и повторяемость
1. Сохранить seed в каждом результате, сейчас seed не показывается пользователю как обязательная часть результата.
2. Хранить параметры, подпись колод и версию карточной базы.
3. Подключить хранение матриц в интерфейсе или удалить неиспользуемую заготовку store, если сценарий не подтверждён.
4. Добавить экспорт полного набора событий партии.

## 3. P1 — Качественный локальный beta и подготовка hosted beta
- Responsive интерфейс для рабочего сценария на ПК и планшете.
- Ясные состояния загрузки, ошибки, отмена долгой задачи.
- Понятный первый путь: вставить две колоды → декодировать → выбрать режим → запустить → понять результат.
- Обозначение model-based estimate и список ограничений, затронутых картами.
- Контроль количества партий, времени и размера ответа.
- Hosted preview на HTTPS после локальной проверки и базовой политики приватности.
- Гостевой режим на старте; аккаунты не обязательны.

## 4. P2 — Аналитика и Deck Workshop
- Полный просмотр реплея с журналом всех действий.
- Множественные winlines и смешанные комбинации.
- Goldfish анализ и вероятности сборки планов.
- Доверительные интервалы/оценка неопределённости winrate.
- Тепловая матрица с фильтрами, быстрым открытием матчапа и сохранёнными матрицами.
- Baseline/draft, diff колод, undo/redo и пакетные проверки замен.
- Экспорт отчёта с настройками, журналами и объяснениями.

## 5. P3 — Облачные данные и масштабирование
- Аккаунты и серверное хранение после подтверждения спроса.
- Синхронизация deck library и истории между устройствами.
- Очередь фоновых задач и отдельные backend workers для крупных запусков/матриц.
- Кеш результатов по сигнатурам колод, версии правил и параметрам.
- Мониторинг и лимиты, чтобы длинная задача не зависела от открытой вкладки.

## 6. P4 — PWA и мобильная упаковка
- Сначала responsive web.
- Затем manifest, иконки, установка как PWA и осторожный offline cache.
- Проверка на Android/iOS.
- Capacitor — если потребуется публикация в магазинах или нативные функции.
- React Native не начинать без конкретной причины: это отдельная UI-кодовая база.

## 7. P5 — Meta и сообщество
- Каталог публичных колод, подборки и теги.
- Импорт из внешних каталогов только через доступные и разрешённые источники.
- Статистику реальных матчей держать отдельным слоем от симуляции; не смешивать наблюдаемые данные с model-based estimate.

## 8. Правила статуса задач

- **Done** — есть тест/демонстрация, подтверждающая пользовательское поведение.
- **Implemented, not verified** — код есть, но поведенческая проверка не проведена.
- **Blocked** — известная проблема блокирует сценарий.
- **Planned** — кода ещё нет.
- Успешный TypeScript/build не доказывает игровую корректность.
- Результат одной тестовой колоды не доказывает общее качество модели.
- Roadmap меняется при появлении фактов из reverse engineering и реальных тестов.
