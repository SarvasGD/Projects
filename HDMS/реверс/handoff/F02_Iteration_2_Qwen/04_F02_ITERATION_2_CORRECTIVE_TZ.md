## 3. Обязательное разделение типов утверждений

В обоих результатах каждый существенный пункт классифицируй:

- **DF — Donor Fact:** что делает Firestone, с доказательством.
- **HR — HDMS Requirement:** что уже требуется HDMS действующими документами.
- **HR owner clarification:** прямое продуктовое уточнение владельца, данное в этом пакете.
- **DI — Derived Implication:** техническое следствие или рекомендуемое решение, вытекающее из DF и HR.
- **PR — Proposal:** необязательный вариант.
- **OD — Owner Decision:** только крупное решение, которое нельзя вывести из документов, прямых указаний владельца и допустимых источников.

Не повышай DI до HR. Наблюдение у Firestone не становится автоматически требованием HDMS. Отсутствие у Firestone не отменяет требование HDMS.

### 4.2. Контрольная схема состояний — используй как обязательную гипотезу для сверки, а не как замену исследованию

Исходный код уже был независимо прочитан в ходе постановки этого задания. На контрольном snapshot обнаружена следующая цепочка; проверь её полностью и укажи точные доказательства:

**A. Первоначальное состояние менеджера наборов**
- SetsManager создаёт собственный BehaviorSubject для sets с начальным значением пустого массива.
- При первом подписчике подписывается на CollectionManager.collection$$ с debounceTime.
- Каждое пришедшее значение коллекции нормализуется выражением nullish → [].
- Затем строятся все наборы из справочника.

**B. Построение карточек наборов**
- Для каждой карточки каждого набора выполняется точный поиск исходной записи коллекции по card.id.
- Если запись есть, переносятся счётчики обычных, золотых, алмазных и сигнатурных копий.
- Если записи нет, все четыре счётчика становятся 0.
- То есть результат — не сырой список карт пользователя и не пустой список; это полный список карт набора, снабжённый количеством владения (в том числе нулевым).

**C. Формирование collection$ в DeckBuilder**
- DeckBuilder берёт sets stream, собирает все set.allCards в один плоский массив SetCard.
- У этого потока есть собственная начальная эмиссия, происходящая из начального пустого sets.
- Поэтому начальный collection$ может быть пустым массивом, даже до получения полного набора SetCard.
- Различай этот промежуточный пустой emission и steady-state результат после построения всех наборов.

**D. Передача в DeckListStatic**
- DeckBuilder передаёт collection$ в input дочернего компонента списка карт.
- Setter дочернего компонента при пустом массиве нормализует его внутреннее значение в null.
- При непустом массиве SetCard строит словарь владения по id с четырьмя счётчиками.

**E. Алгоритм маркера нехватки**
- Когда внутренняя коллекция для построения строки равна null, код считает inCollection = true, поэтому isMissing = false.
- Когда передан словарь по полной коллекции SetCard, проверка владения использует агрегацию по цепочке counterpart-карт; сравнивает агрегированное владение с необходимым количеством.
- Следовательно, при полном списке SetCard с нулевым владением карты считаются отсутствующими (если ни одна из counterpart-версий не имеет владения).
- Если у нужной карты exact ID владения нет, но у counterpart-версии оно есть, маркер может считать карту имеющейся благодаря агрегации.

**F. Независимый алгоритм missing dust**
- Dust stream использует current deck cards и плоский collection$.
- Для каждой уникальной карты ищет SetCard по точному card ID.
- Если записи нет, owned = 0. Если запись есть, берёт суммарное владение из самой SetCard.
- missing copies = max(0, needed copies − exact-ID owned).
- missing copies умножаются на craft dust cost по rarity; затем суммы складываются.
- Этот путь не использует counterpart aggregation.
- Поэтому на состоянии, когда полный набор SetCard построен с нулевым владением, и маркер нехватки, и dust считают карты отсутствующими.
- Но при наличии owned counterpart-версии и отсутствии owned exact-ID версия маркер может считать карту имеющейся, а dust по-прежнему может начислять стоимость для exact ID. Это реальное расхождение двух алгоритмов.
