Это не задача по разработке функциональности HDMS. Код продукта и код Firestone не изменять.

## 5. Этап B — исправить F-01 и связанные выводы

Восстанови всю последовательность состояний, а не только поведение отдельного setter.

Обязательно отрази:

1. начальное состояние потока SetsManager;
2. первоначальный пустой emission;
3. нормализацию отсутствующей коллекции в пустой массив на upstream-уровне;
4. построение полного списка карт набора с нулевыми счётчиками владения;
5. преобразование наборов в плоский список SetCard для конструктора;
6. передачу этого списка компоненту списка колоды;
7. временное поведение при первоначальном пустом массиве;
8. итоговое поведение после получения полного списка карт с нулевым владением;
9. отдельную проверку владения для маркера нехватки с учётом counterpart-версий;
10. отдельный расчёт пыли по точному ID и стоимости создания по редкости.

Используй точные permalink и диапазоны строк для всех звеньев. Не объединяй:
- initial empty emission;
- unknown/not yet loaded;
- отсутствующую коллекцию;
- полный набор карточек с нулевым владением;
- нормализованный словарь владения;
- UI-маркер нехватки;
- сумму пыли.

**Исправь E-25:** ожидание «Пыль = 0» при непустой колоде и нулевом владении неверно. При нулевом владении расчёт missing dust даёт стоимость создания требуемых карт по редкости. Маркер списка колоды проходит отдельный путь и может вести себя иначе на первоначальном пустом emission.

**R-37-HR не считать готовым фактом или ранее утверждённым требованием.** Сохрани исходное донорское расхождение как DF. Единый учёт counterpart-версий для маркера и пыли можно оставить как DI — рекомендуемое решение для HDMS, с обоснованием: одинаковое владение не должно одновременно отображаться как «карта имеется» и как полная стоимость её создания. Не приписывай этот вывод Feature List или прямому решению владельца. Не выноси это как мелкий вопрос владельцу.

Явное состояние «коллекция неизвестна/загружается» также описывай как DI или целевой UX-контракт, а не как подтверждённое поведение Firestone.

Сохрани формулу пыли по редкости и явно укажи значения: Common — 40, Rare — 100, Epic — 400, Legendary — 1600. Убедись, что источник относится к вызываемой функции и закреплённому snapshot.

### C-03. Классификация фактов и требований

Во всём итоговом документальном пакете последовательно различай:
- DF — Donor Fact;
- HR — HDMS Requirement;
- HR owner clarification — прямое уточнение владельца;
- DI — Derived Implication;
- PR — Proposal;
- OD — Owner Decision, только если крупное решение действительно осталось открытым.

Для HR указывай конкретный источник HDMS и раздел/строку. Прямые уточнения владельца не выдавай за цитаты из Feature List.

### C-04. Трассировка AC → TC

Исправь AC-11:
- руны — R-20…R-22 и TC-24…TC-26;
- туристы — R-05 и TC-44.

TC-05 описывает обычный пул класса Mage в Standard и не является тестом туриста. Не ссылайся на него как на доказательство туристического расширения.

Перепроверь и другие AC → TC ссылки. Не утверждай покрытие, если тест не проверяет ожидаемое поведение.

TC-45 может оставаться как тест на согласованность counterpart-версий, но его ожидаемый результат должен быть помечен как проектное решение DI, а не уже существующее HR. TC-46 — целевой HDMS-тест семантического сохранения колоды через экспорт/импорт, а не доказательство внутренней гарантии Firestone или внешней библиотеки.

Сохраняй существующие ID. Новые тесты нумеруй после последнего занятого ID; не перенумеровывай первую итерацию.

### C-05. Deckstring

Зафиксируй в Evidence Register:
- собственный код Firestone, который вызывает encode/decode;
- функцию предварительной обработки, если она no-op;
- компонент и контракт экспорта;
- версию внешней зависимости из package manifest;
- границу Unknown: содержимое и гарантии внешней библиотеки не подтверждены, если её код отдельно не исследован.

Не заявляй byte-for-byte round-trip. В целевом HDMS-тесте сравнивай семантическое содержимое декодированной колоды.

### C-06. Дата и clean-room

## 11. GitHub и контроль изменений

- Работай от свежего main; перед изменениями зафиксируй HEAD.
- Не используй force push.
- Не меняй код HDMS и код Firestone.
- Не меняй Feature List из-за отсутствия функции в Firestone.
- Не перезаписывай исходные документы первой итерации.
