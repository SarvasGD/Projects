# F02 Firestone — корректировка результата третьей итерации и база для финального реверса

**Назначение:** независимый контроль и восстановление целостности материалов после третьей итерации реверса.  
**Функция:** F02 — визуальный конструктор колод.  
**Донор:** только Firestone.  
**Закреплённый snapshot:** commit 0a30f066eb77a417637d95cec86444456f607ba1 (2026-02-08T20:08:36Z).  
**Статус текущих документов:** REVISION REQUIRED как итоговые проектные документы; исследовательские выводы по ключевым исправлениям в основном подтверждены.  
**Решение:** не начинать исследование с нуля. Использовать восстановленную историю и выполнить одну финальную полную редакцию Function Spec и Evidence Register.

## 1. Что проверено и почему предыдущий результат оказался неполным

Проверены:
- полный Function Spec и Evidence Register первой итерации;
- полный отчёт независимого контроля второй итерации;
- фактически сохранённый черновик Function Spec и Evidence Register второй итерации из архива;
- два документа, полученные от реверс-инженера в третьей итерации;
- исходники Firestone на закреплённом commit по сквозной цепи коллекции и пыли, форматам, коду колоды и связанным компонентам;
- история идентификаторов и трассировка утверждений.

Важное уточнение о входных материалах: Function Spec первой итерации и Evidence Register первой итерации сохранились полностью. Документ Function Spec второй итерации в истории представлен коротким корректирующим черновиком, а не полной спецификацией. Следовательно, замечание владельца о неполной передаче документа через Markdown-блок вполне могло повлиять на работу третьего исполнителя и объясняет часть ссылок «см. Итерацию 1». При этом полная база первой итерации была доступна в объединённом входном файле. Финальный исполнитель должен был восстановить цельный документ на её основе, а не оставлять ссылки на отсутствующие разделы.

Текущие документы третьей итерации содержат полезные исправления, но не являются самодостаточной полной редакцией:
- Function Spec §6, §8, §9, §10, §11 ссылаются на Итерацию 1 вместо включения полных сценариев, состояний, контрактов, edge cases и тест-кейсов.
- Evidence Register не содержит полноценного журнала и карточек EV с точными путями, диапазонами строк и постоянными ссылками; он описывает результаты таблицами, но не даёт независимому проверяющему воспроизвести каждое утверждение.
- часть новых идентификаторов повторно использует номера, которые уже имели другое значение в предыдущем черновике.
- §14 Function Spec говорит, что все вопросы владельца из первой итерации сохраняются, хотя несколько из них уже решены прямыми уточнениями владельца.

Это дефекты оформления и целостности результата, а не основание выбрасывать подтверждённое исследование.

## 2. Сквозная цепь коллекции и пыли — контрольная модель

Ниже приведена модель, которую финальная редакция обязана отразить без объединения разных уровней состояния.

| Этап | Факт по исходникам | Следствие |
|---|---|---|
| 1. Источник коллекции | Внутренний поток коллекции создаётся с начальным значением null; CollectionManager публикует именно этот поток | Начальное значение источника теперь известно, это не Unknown |
| 2. Менеджер наборов | Поток наборов изначально содержит пустой массив. Подписка на коллекцию начинается при первой подписке; источник проходит debounceTime(1000) | До построения каталога существует начальное пустое состояние потока наборов |
| 3. Нормализация источника | В callback применяется collection ?? [] | Нормализуются null и undefined, а не любые falsy-значения |
| 4. Полный каталог | Для всех карт всех наборов строятся SetCard-записи; поиск владения — по точному ID; если запись не найдена, четыре счётчика владения равны нулю | После построения каталога получается полный список карточек с нулевым владением, а не пустая коллекция |
| 5. Плоский список | Конструктор разворачивает карточки всех наборов в один список; у потока есть собственная начальная пустая эмиссия | В дочерний компонент может прийти пустой массив до полного каталога |
| 6. Передача | Плоский список передаётся во вход collection компонента списка колоды | Нельзя смешивать начальное значение источника, поток наборов и вход дочернего компонента |
| 7. Нормализация входа | Пустой или отсутствующий массив сбрасывает внутренний normalizedCollection в null; непустой каталог превращается в словарь владения | Внутренний null дочернего компонента — не то же самое, что null источника CollectionManager |
| 8. Маркер | При внутреннем null карты считаются имеющимися; при словаре владение считается через агрегацию альтернативных версий карты | Маркер может считать карту имеющейся, если пользователь владеет другой версией |
| 9. Пыль | Отдельный расчёт ищет карту по точному ID в плоском каталоге, получает owned=0 при отсутствии записи и считает max(0, needed-owned) × стоимость по редкости | При непустой колоде с известной редкостью и нулевом владении начисляется полная стоимость недостающих копий; пыль не равна нулю |

### 2.1. Разделение состояний

| Состояние | Вход списка колоды | Маркер | Пыль |
|---|---|---|---|
| Начальный пустой поток наборов / пустой плоский список | Пустой массив нормализуется во внутренний null | Внутренне карта считается имеющейся; нельзя утверждать, что пользователь обязательно успевает увидеть это состояние | Для непустой колоды с известной редкостью точный поиск не находит карту: считается полная стоимость недостающих копий |
| Установившийся полный каталог, коллекция отсутствует или пуста | Полный каталог, все счётчики владения нулевые | Карта отсутствует, если ни одна альтернативная версия не имеет владения | Полная стоимость недостающих копий |
| Полный каталог с обычным владением точной версии | Полный каталог с реальными счётчиками | Маркер учитывает владение по альтернативным версиям | Пыль учитывает владение по точному ID |
| Владение есть только у альтернативной версии | Полный каталог | Маркер может считать карту имеющейся | Пыль может начислить стоимость точной версии; это подтверждённое расхождение донора |

Условия и ограничения:
- Для пустой колоды сумма пыли равна нулю естественным образом.
- Если редкость не определена, текущая функция стоимости возвращает значение по ветке default; в спецификации следует точно описать таблицу и не делать выводов о неизвестных данных карты.
- Нельзя утверждать конкретный порядок пользовательских рендеров или видимость промежуточного состояния без запуска приложения.
- Нельзя писать, что начальное значение источника коллекции неизвестно: оно равно null в исходном коде.
- Нельзя писать «любое ложное значение»: оператор ?? нормализует null/undefined.

## 3. Другие исправления, которые следует сохранить

### F-02. Форматы
- Факт донора: интерфейс выбора предлагает Standard и Wild; Twist закомментирован.
- Наличие ветвей кода для других форматов не доказывает фактическую поддержку: выбор наборов зависит от внешней конфигурации.
- Требование HDMS: конструктор колод на текущем этапе — Standard. Это не поддержка Wild-колод.
- Wild-only карты/сущности допустимы в карточной базе и симуляции, когда их создаёт/призывает карта, легальная в Standard. Это не меняет формат колоды.
- Источник интерфейса: [constructed-deckbuilder-format.component.ts, L41-L53](https://github.com/Zero-to-Heroes/firestone/blob/0a30f066eb77a417637d95cec86444456f607ba1/libs/legacy/feature-shell/src/lib/js/components/decktracker/main/deckbuilder/constructed-deckbuilder-format.component.ts#L41-L53).
- Не объявлять Classic/Twist поддерживаемыми только по условным ветвям кода. Внешний конфиг — отдельный, изменяемый источник и не привязан к snapshot.

### F-03. Drag-and-drop
- В проверенном объёме файлов конструктора реализация перетаскивания не обнаружена.
- Нельзя делать вывод об абсолютном отсутствии механики во всём продукте или приписывать обработчикам мыши неподтверждённое назначение.
- Для HDMS drag-and-drop остаётся требованием Feature List. Отсутствие у донора не отменяет и не понижает требование.

### F-04. Источники требований
В спецификации строго разделять:
- DF — Donor Fact: подтверждённое поведение Firestone;
- HR — утверждённое требование HDMS из Feature List/документов/решения владельца;
- HR-OC — прямое уточнение владельца;
- DI — рекомендация аналитика, не утверждённое требование;
- OR — Owner decision required, только реальный крупный продуктовый выбор;
- Unknown / Not found — отсутствие доказательства в конкретно обозначенном объёме.

DI-01 (единый алгоритм владения для маркера и пыли) остаётся рекомендацией, а не требованием HDMS.

### F-05. Тесты и трассировка
- TC-44 должен проверять пул через карту-туриста. Обычный пул класса мага и тесты рун не подтверждают поведение туриста.
- Требования к рунам и туристу — разные механики. Для туриста использовать правило R-05 (карта-турист), а не R-20…R-22 (руны).
- Для каждого AC проверить, что связанные TC действительно проверяют его формулировку. Не оставлять ссылки на тесты токена поиска, когда критерий относится к лимиту копий.
- Сохранить TC-43…TC-46 как новые/уточнённые кейсы, если их предусловия, действия и ожидаемые результаты остаются согласованными с полной спецификацией.

### F-06. Код колоды
- Предобработка определения колоды в исследованной обвязке тождественна: возвращает вход без изменений.
- Кодирование/декодирование делегировано внешней библиотеке; её внутренние гарантии не исследовались.
- Не заявлять round-trip guarantee от имени Firestone. В HDMS целевой тест должен проверять семантическую эквивалентность состава колоды, количества, героя, формата и вложенных наборов, а не побайтовое равенство строк.
- Источники: [deck-utils.ts, L1-L21](https://github.com/Zero-to-Heroes/firestone/blob/0a30f066eb77a417637d95cec86444456f607ba1/libs/legacy/feature-shell/src/lib/js/components/decktracker/main/deckbuilder/deck-utils.ts#L1-L21) и [package.json, L104](https://github.com/Zero-to-Heroes/firestone/blob/0a30f066eb77a417637d95cec86444456f607ba1/package.json#L104).

### 4.2. Rule ID
- Существующий R-46 из прежней спецификации сохраняет своё исходное значение (тождественная предобработка кода колоды).
- Текущая новая запись о потоке наборов не может называться R-46. Назначить ей R-47.
- Полный каталог перенумеровать в R-48.
- Плоский список перенумеровать в R-49.
- Ссылки на эти правила синхронно обновить в Function Spec, Evidence Register, edge cases и тестах.

### 4.3. Edge Case ID
- E-01…E-23 сохраняются из полной первой спецификации.
- E-24 и E-25 уже встречались в черновике второй итерации и имели другое содержание; не переопределять их задним числом.
- Три состояния из текущего документа перенумеровать:
  - транзитивная пустая эмиссия → E-26;
  - полный каталог с нулевым владением → E-27;
  - владение только альтернативной версией → E-28.
- Все ссылки на edge cases и тесты обновить.

### 4.4. Test ID
TC-43…TC-46 оставить за соответствующими новыми тестами третьей итерации после проверки их связи с AC. TC-01…TC-42 восстановить из полной спецификации первой итерации. Не использовать многоточия вместо тест-кейсов.

## 5. Продуктовые решения владельца, уже известные и не подлежащие повторному запросу

1. Текущий формат конструктора HDMS — Standard.
2. Wild-only карты/сущности допускаются только как создаваемые или призываемые Standard-легальными картами; это не Wild deckbuilding.
3. Drag-and-drop остаётся требованием Feature List.
4. Карточная база предусмотрена; полнота повышается итерациями до 100% поддерживаемого scope.
5. Стоимость создания выводится из редкости по справочнику/формуле; отдельное хранимое поле стоимости не требуется.
6. Отсутствие функции у Firestone не отменяет требования HDMS.
7. Мелкие технические вопросы, обычные edge cases и уточнения поведения зависимостей исполнитель решает по источникам и тестам. Владельцу выносятся только крупные неразрешимые продуктовые решения, реальные противоречия требований и серьёзные правовые риски.

Старые вопросы о Standard/Wild и о том, сохранять ли drag-and-drop, закрыты. Не возвращать их в §14 как открытые вопросы.

Sideboards, undo/redo, персистентность черновика, строгая валидация импорта и идемпотентность сохранения могут оставаться вопросами только если актуальные Feature List/Roadmap действительно не дают ответа и выбор влияет на продуктовый scope. Не переносить автоматически весь старый список вопросов владельцу.

## 6. Полнота итоговых документов

Финальная Function Spec должна быть самостоятельной:
- включить полные разделы первой итерации, которые не отменены;
- включить все исправления третьей итерации;
- не использовать формулировки «сохраняется из Итерации 1», «см. предыдущую версию», «все кейсы сохраняются» вместо текста;
- не оставлять ссылки на документы, которые исполнитель должен вручную объединять;
- сохранить нейтральную терминологию и разделение DF/HR/HR-OC/DI/OR;
- не переносить внутренние имена классов/методов/компонентов Firestone в нейтральные требования.

Финальный Evidence Register должен быть самостоятельным:
- включить полный журнал и карточки EV-001…EV-137 с сохранением исходного смысла старых идентификаторов;
- не дублировать номер EV с новым значением;
- для каждого существенного нового факта дать точный путь, commit SHA, permalink, диапазон строк, вывод и ограничения доказательства;
- связать EV с R/E/TC;
- не считать наличие имени файла доказательством полного пользовательского сценария.

## 7. Clean-room

**Принцип clean-room сохраняется.** Текущая работа описывает наблюдаемое поведение донора, ограничения доказательств и нейтральные требования HDMS. В Function Spec нельзя переносить исходный код, близкий псевдокод, внутреннюю архитектуру или внутренние имена Firestone. В Evidence Register технические имена и пути допустимы только как координаты первичного источника для проверки.

Использование Firestone как единственного назначенного донора в рамках этого исследования не означает разрешения копировать его реализацию. Лицензионный статус донора остаётся неподтверждённым; не делать юридических выводов сверх имеющихся данных.

## 8. Результат контроля и следующий шаг

- Сквозная логика F-01 подтверждена по исходникам; ошибка «пыль = 0» устранена.
- Начальное значение источника коллекции установлено: null. Это больше не Unknown.
- Текущие документы третьей итерации не принимаются как финальные из-за неполноты и конфликтов идентификаторов.
- Полная база первой итерации сохранена; короткий документ второй итерации используется только как история корректировок.
- Повторная деконструкция с нуля не требуется.
- Следующий и последний проход реверс-инженера должен выдать ровно два полных документа: Function Spec Iteration 3 и Evidence Register Iteration 3. Исполнитель получает этот отчёт, полную базу первой итерации, черновики третьей итерации и архивный черновик второй итерации.
- После этого проводится короткая независимая проверка исправленных документов. Новые доноры, изменение Feature List/Roadmap и реализация кода в этот проход не входят.

**Критерий готовности:** два самодостаточных документа, восстановленная трассировка EV/R/E/TC/AC без коллизий, все подтверждённые исправления включены, неизвестное честно помечено, продуктовые решения владельца не подменены рекомендациями.
