# HDMS — как экономить токены при деконструкции

## Главный принцип

Не заставляйте ИИ повторно читать и пересказывать уже изученный репозиторий. Используйте готовые документы Qwen как базу, независимый отчёт — как список точечных задач, а новый результат оформляйте дополнением.

## Рекомендуемый рабочий цикл

| Этап | Что делает ИИ | Что сохраняет | Почему это экономит токены |
|---|---|---|---|
| 0. Подготовка | Читает brief, аудит и оглавления исходных документов | Короткий список задач F-01…F-06 | Не перечитывает весь пакет без цели |
| 1. Точная проверка | Открывает только необходимые файлы и диапазоны строк | Evidence ID + путь + SHA + строки | Не загружает в контекст большие файлы целиком |
| 2. Трассировка | Сопоставляет конкретные утверждения, правила, тесты и источники | Таблица AC → TC → EV | Избегает повторного описания функциональности |
| 3. Дополнение | Записывает новые/исправленные сведения | Один `Continuation_Addendum.md` | Не переписывает два больших исходных документа |
| 4. Самопроверка | Проверяет ссылки, диапазоны, ID, открытые вопросы | Чек-лист завершения | Ловит ошибки до повторного аудита |
| 5. Handoff | Сохраняет завершённое и незавершённое | Краткий handoff в дополнении | Позволяет продолжить в новом чате без полного восстановления контекста |

## Практические правила

### 1. Работать порциями, а не одним огромным заданием

Для функции № 2 разумно выполнять исследование блоками:

- блок A: данные коллекции и пыль;
- блок B: форматы, классы и легальность пула;
- блок C: импорт, экспорт и sideboards;
- блок D: сохранение и восстановление состояния;
- блок E: тест-кейсы и трассировка критериев приёмки.

Каждый блок должен иметь конкретный вопрос и результат. Не просите агента «ещё раз полностью исследовать Firestone».

### 2. Не копировать исходники в чат

Вместо длинных вставок достаточно:

`EV-120 | path/to/file.ts | commit SHA | L120-L148 | подтверждает X, не подтверждает Y | R-46 / TC-43`

В итог переносите только смысл доказательства и ссылку. Большие исходные фрагменты быстро расходуют контекст и усложняют поиск противоречий.

### 3. Вести Evidence Register по ходу исследования

Не откладывайте ссылки, строки и ID «на потом». Фиксируйте их сразу при чтении файла. Иначе агенту придётся повторно открывать тот же код, восстанавливать номера строк и заново объяснять уже найденное.

Не дублируйте карточки доказательств. Если новое утверждение уже покрывает старый EV, добавьте уточнение или ссылку на него; новый ID используйте только для нового факта или исправленного доказательства.

### 4. Разделять роли и не дублировать параллельную работу

Один агент — один конкретный участок. Не запускайте двух агентов читать одни и те же компоненты с просьбой сделать одинаковое резюме. Параллельная проверка полезна только при независимых задачах и чётком общем формате результата.

### 5. Ограничивать глубину там, где она не нужна

Для поиска файла, сверки номера строки или инвентаризации тестов достаточно короткого технического прохода. Глубокий анализ оставляйте для сложных цепочек данных, конфликтов состояний и причинно-следственных выводов.

Не отключайте глубокую проверку везде: экономия не должна превращаться в поверхностные утверждения.

### 6. Устанавливать лимит и критерий остановки

Если конкретный инструмент поддерживает лимит хода, бюджета, времени или количества итераций — задайте его до запуска. Не считайте лимит отдельного хода гарантией общего бюджета.

Лучше ограничивать не только токены, но и объём задачи: например, «проверить F-01 на 5 конкретных файлах и выдать таблицу состояний», а не «разобраться со всем конструктором».

### 7. Делать сохранённый handoff до исчерпания контекста

После каждого значимого этапа сохранить:

- текущий commit SHA;
- проверенные файлы и диапазоны;
- новые Evidence ID;
- подтверждённые выводы;
- оставшиеся вопросы;
- точный следующий шаг.

Если агент неожиданно остановится, handoff позволит продолжить без повторного исследования.

### 8. Разделять исследование и оформление

Сначала соберите точные факты и связи. Только после этого пишите вывод. Не просите агента каждый раз пересказывать всю спецификацию после проверки одного источника.

Для промежуточного сообщения достаточно трёх строк: `проверено`, `найдено`, `следующий шаг`.

## Рекомендуемый лимит вывода

| Вид результата | Практический размер |
|---|---:|
| Сообщение о ходе работы | 3–6 коротких пунктов |
| Ответ по одному спорному утверждению | 1 таблица, 5–10 строк |
| Handoff между сессиями | 300–700 слов |
| Итоговый чат-ответ | до 1 000 слов |
| Полный Evidence Register / Addendum | отдельный файл, без повторения старого содержания |

Это ориентиры по объёму результата, а не универсальные тарифные лимиты модели.

## Что не делать

- Не читать все файлы Firestone, если задача касается одного сценария.
- Не перечитывать 93 КБ спецификации и 143 КБ Evidence Register в каждом новом ходе.
- Не просить объяснить повторно каждый EV, уже описанный в исходном реестре.
- Не генерировать новый полный отчёт после каждой небольшой правки.
- Не поручать агенту решать продуктовые вопросы вместо владельца.
- Не закрывать неизвестное собственным предположением.
- Не считать уверенный ответ доказательством выполнения задачи.

## Применение к текущей задаче HDMS F02

Следующему ИИ достаточно начать с:

1. этого регламента;
2. отчёта независимого контроля;
3. Function Spec — только спорные разделы;
4. Evidence Register — только нужные Evidence ID;
5. точных исходников Firestone по F-01…F-06.

**Не нужно повторять исходную деконструкцию.** Цель — адресно закрыть замечания и подготовить проверяемое дополнение.
