# Матрица доноров и целевых функций

**Статус:** фиксированное распределение для первого контура реверс-инжиниринга.  
**Дата актуализации:** 17 ноября 2026.

| Firestone | https://github.com/Zero-to-Heroes/firestone | **Не подтверждён; считать не-OSS** | Repository API возвращает license:null; в README нет лицензии, а в дереве master не найден LICENSE/COPYING. | Fireplace | https://github.com/jleclanche/fireplace | **Да** | GNU AGPL v3 | В периметре исследования; учитывать copyleft и сетевые условия, если использование кода будет отдельно рассматриваться |
| MetaStone | https://github.com/demilich1/metastone | **Да** | GNU GPL v2 | В периметре исследования; учитывать условия GPL, если использование кода будет отдельно рассматриваться |

**Итог по терминологии:**
- Все пять проектов входят в закрытый перечень публичных проектов для исследования.
- По состоянию на проверку 17.11.2026, три из пяти имеют подтверждённую open-source лицензию: hearthstone-oracle, Fireplace и MetaStone.
- HDT не является open-source проектом: в README прямо указано All Rights Reserved.
- Для Firestone есть противоречивый сигнал: страница-список организации показывала MIT-0, но repository API возвращает license:null, README не содержит лицензии, а дерево master не содержит LICENSE/COPYING. До подтверждения лицензии владельцем Firestone не классифицировать как open source и не использовать код.
- Термины «публичный репозиторий», «доступный исходный код» и «open source» не взаимозаменяемы.

Это **не меняет закрытый исследовательский периметр**: HDT и Firestone остаются разрешёнными проектами для изучения их публично доступного поведения и материалов. Исследование не означает разрешение копировать их исходный код.

Для каждого запуска исследования фиксировать canonical URL, ветку/tag, commit SHA, дату и сведения о лицензии. Проверять не только лицензию репозитория в целом, но и лицензии отдельных файлов, зависимостей, изображений, текстов и карточных данных. Лицензия проекта не распространяется автоматически на сторонние материалы, которые он использует.

## 2. Семь функций: ровно один основной донор

| № | Целевая функция | Единственный основной донор | Что исследовать | Что не исследовать в этом пакете |
|---|---|---|---|---|
| 1 | Плагинная архитектура | HDT | Расширения, жизненный цикл, точки интеграции, события, конфигурация, совместимость и изоляция сбоев | Другие plugin-системы и плагины как самостоятельные продукты |
| 2 | Визуальный конструктор колод | Firestone | Создание, редактирование, поиск, фильтры, слоты, валидация, состояния интерфейса | Конструкторы FindStone/HSReplay и альтернативные реализации |
| 3 | Визуализация мана-кривой | Firestone | Группировка стоимости, подсчёт, пересчёт, связь с колодой, интерактивность и edge cases | Реализация кривой в HDT, hearthstone-oracle и других проектах |
| 4 | Сбор пользовательской матчевой статистики | HDT | События матчей, состав записей, локальное хранение, настройки сбора, импорт/экспорт | HSReplay, его серверная статистика и любые закрытые backend-механизмы |
| 5 | Реестр эффектов карт | Fireplace | Каталог карт/эффектов, модель триггеров, повторное использование эффектов, статусы поддержки, тесты | Реестр и движок MetaStone; сравнение двух симуляторов выполняет только третий агент |
| 6 | LLM-ассистент анализа архетипа | hearthstone-oracle | Карточная база, декодирование, стратегические знания, анализ архетипа, формат объяснений и инструменты | Другие LLM-ассистенты и закрытые аналитические сервисы |
| 7 | UI-паттерны Hearthstone companion | Firestone | Навигация, информационная иерархия, карточные представления, подсказки, состояния и responsive | FindStone, HSReplay и самостоятельное сравнительное UX-исследование |

Один и тот же донор может быть назначен нескольким разным функциям. Это допустимо, потому что предметные срезы и вопросы исследования различаются. В рамках каждой строки основной донор ровно один.

## 3. Отдельная сквозная задача полного игрового движка

| Задача | Единственный основной донор реверс-инженера | Назначение |
|---|---|---|
| Полная физика игры, правила матча и взаимодействия карточных эффектов | MetaStone | Модель состояний, фазы, действия, события, триггеры, разрешение эффектов, бой, смерть, случайность и взаимодействия механик |

Полная физика — самостоятельная центральная задача ядра HDMS, а не только реестр эффектов и не дополнительная UI-функция. MetaStone назначен единственным основным донором реверс-инженера именно для этой задачи. Реверс-инженер не обращается к Fireplace или другим донорам для заполнения пробелов.

## 4. Строгое разделение ролей при проверке

1. **Реверс-инженер первого контура** исследует только назначенного донора по конкретной функции. Он не сравнивает доноров, не открывает альтернативные проекты и не пытается самостоятельно закрывать обнаруженные пробелы сведениями из других источников.
2. **Третий агент-проверяющий** получает готовые спецификации, evidence register и список пробелов. Только он выполняет независимую перекрёстную проверку по другим проектам из разрешённого списка и по отдельным достоверным источникам игровых правил. Он не превращает это в повторное полное исследование всех доноров.
3. **Владелец HDMS** принимает продуктовые решения по обнаруженным расхождениям, неизвестным случаям и границам scope.
4. **Агент-разработчик** получает только утверждённые нейтральные спецификации, тест-кейсы и разрешённые данные. Он не получает донорские исходники и не ищет их самостоятельно.

FindStone и HSReplay исключены из исследования всеми участниками.

## 5. Почему такая декомпозиция

- HDT выбран для исследования расширяемости и локального учёта матчей.
- Firestone выбран для пользовательского конструктора, мана-кривой и companion UI-паттернов.
- Fireplace выбран для модели реестра карточных эффектов и их тестового покрытия.
- hearthstone-oracle выбран для LLM-анализа состава колоды и архетипа.
- MetaStone выделен для полной модели игровых правил и разрешения взаимодействий карточных эффектов.

Это фиксированное организационное распределение для первого контура, а не утверждение, что назначенный донор является безусловно лучшим, актуальным или полным эталоном.

## 6. Правило пробелов

Если назначенный проект не содержит требуемой информации, версия проекта устарела или функция не подтверждена:
1. реверс-инженер фиксирует отсутствие/неопределённость;
2. не открывает другой донор по собственной инициативе;
3. не подменяет отсутствующие сведения собственным предположением;
4. передаёт пробел третьему агенту для отдельной проверки;
5. владелец HDMS принимает решение после проверки.

Нельзя считать функцию или карту покрытой только потому, что исследование назначенного донора завершено. Цель HDMS — полная физика всех карт в поддерживаемом scope; фактическая полнота подтверждается тестами и независимой проверкой, а не предположением о возможностях пяти проектов.
