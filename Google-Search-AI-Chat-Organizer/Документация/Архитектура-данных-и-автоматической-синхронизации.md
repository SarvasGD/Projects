# Архитектура данных и автоматической синхронизации
**Актуальность:** 23.11.2026

## 1. Владение данными

**Google AI Mode history — источник истины о существовании, названии и состоянии диалогов.**

| Данные | Источник истины | Локальная роль |
|---|---|---|
| Наличие диалога | Google | Последнее синхронизированное состояние |
| Заголовок и порядок | Google | Обновляемый кэш |
| Thread/session ID | Google DOM/URL | Стабильный ключ папочного назначения |
| Папки, подпапки, цвет и порядок | Органайзер | Локальные пользовательские метаданные |
| Число реплик пользователя | Содержимое сессии | Вычисляемый кэш, не source of truth |
| Полнотекстовый индекс | Содержимое сессии | Локальный индекс для поиска и Markdown |

Локальная запись не создаёт существующий Google-диалог. Внешние добавление, переименование, продолжение и удаление автоматически отражаются в органайзере.

## 2. Ключи и identity

Порядок надёжности:
1. Уникальный thread/session/conversation ID, подтверждённый реальным DOM.
2. Подтверждённый identity URL parameter.
3. Обычный q/udm URL — только навигационная ссылка, не identity.
4. Title и кликабельность не являются ключом.

В v0.4.0:
- identity key строится только по thread/session identity parameters, без текста q;
- строки без ID/identity URL идут в «Не классифицировано»;
- title-only fallback исключён;
- неоднозначный ID не используется для переноса папки/индекса.

## 3. Классификация и message count

Различать:
- одноходовую AI activity;
- многоходовой AI Mode conversation;
- неизвестную строку history.

Число реплик — это количество сообщений пользователя, не общее число сообщений. Ответы AI, источники, карточки и UI не считаются user turns.

v0.4.0 добавляет диагностическое чтение явных role markers. Пока реальные Google markers не подтверждены, count остаётся «не определено»; нельзя назначать тип сессии по числу DOM-контейнеров наугад.

## 4. Автоматическая синхронизация

Триггеры:
- открытие/загрузка AI Mode;
- изменение штатной history через MutationObserver;
- SPA-навигация и возврат фокуса на вкладку;
- периодическая лёгкая проверка активной вкладки, если Google не выдаёт событие.

Цикл:
1. Считать штатные history rows, identity и признаки типа.
2. Догрузить список до подтверждённого конца.
3. Классифицировать строки; неизвестные не попадают в активный список чатов.
4. Сопоставить подтверждённые диалоги с folder metadata по стабильному ID, затем identity URL.
5. Добавить новые, обновить изменённые заголовки/порядок/count.
6. После полного списка и подтверждённой identity всех строк убрать отсутствующие verified records из активного набора и освободить их folder binding.
7. Если есть unknown row, lazy loading не завершён или произошла ошибка — destructive reconciliation запрещена.

Пользователю не нужно отдельно удалять локальную запись после удаления в Google. Это отражается обычной синхронизацией.

## 5. Нативное удаление из органайзера

Предложенный сценарий (детали реализации — на пользовательский апрув):
1. Найти точную строку Google по verified thread ID.
2. Вызвать штатное меню строки и Delete.
3. После действия повторно синхронизировать страницу.
4. Удалённая запись исчезает из активного органайзера автоматически.

Если identity неоднозначна — удаление недоступно. Вторую ручную операцию локального удаления не добавлять.

## 6. Ограничения синхронизации

- Отсутствие строки до завершения lazy loading не означает удаление.
- Наличие unknown rows блокирует очистку старых записей.
- Legacy title-only записи не отображаются как чаты, пока не сопоставлены по stable identity.
- Нельзя сливать разные беседы по одному q/названию.
- CI/jsdom подтверждают логику на fixtures, не реальный Google account.


## Fail-open при отсутствии подтверждённой identity

Если после полной загрузки Google history не обнаружено ни одной стабильной identity:
- штатный список остаётся видимым;
- большая overlay-панель не перекрывает исходную историю;
- органайзер показывает только компактную панель ожидания;
- неизвестные строки не становятся активными чатами;
- destructive reconciliation не выполняется.

При наличии хотя бы одного подтверждённого диалога и полной загрузке overlay может заменить список, показывая неизвестные элементы отдельной группой.
